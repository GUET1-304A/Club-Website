## 一、为什么不用 Coze（决策说明）

上次汇报"初步预计使用 Coze 构建智能体"，经深入调研和实际开发后**最终确定自研**。
原因如下：

### 1. 数据无法打通，是根本原因

我们的智能体必须读写自己的数据库：项目、任务、里程碑、周报、提醒、通知。
Coze 的知识库和数据库与我们的系统是两套独立存储：

- 若把数据复制进 Coze → 数据双向不同步，很快出现脏数据；
- 若要实时读写 → 必须写"自定义插件"回调我们自己的 API，
  等于绕一圈最后还是自己开发 HTTP 对接层。Coze 没有省掉开发量，反而多了中间层。

### 2. 权限模型无法对接

系统要求细粒度权限：学生只能操作自己的任务/周报/提醒，教师才能审阅和催收。
这个判断依赖我们后端的 JWT 成员体系，Coze 的机器人没有这个概念。

### 3. 平台锁定与成本不可控

- 限流、配额、费用由平台决定，上线后不可预测；
- 换模型、改逻辑受平台编排能力限制；
- 数据会经过第三方平台，成员信息等敏感数据存在外泄风险。

### 4. 我们具备自研条件

项目已有完整的 Flask REST API、JWT 双身份认证、OpenAI 兼容调用模式（OCR 服务），
自研不需要额外框架，直接在大模型 API 之上加一层"工具调用"即可。

### 对比结论

| 维度 | Coze | 自研（本项目采用） |
|------|------|--------------------|
| 数据同步 | 需插件回调，多一个中间层 | 直接读写自己的库，天然一致 |
| 权限控制 | 无法对接 JWT 成员体系 | 每个工具内部校验权限 |
| 平台依赖 | 高（限流/费用/模型受平台控制） | 无，可随时更换模型厂商 |
| 开发量 | 看似少，实际仍要写对接层 | 一次开发，完全可控 |
| 适用场景 | 访客问答、快速演示 | 本项目业务智能体 |

> **结论**：Coze 留作未来官网"访客问答助手"（招新答疑、FAQ）的入口；
> 业务智能体完全自研。

## 二、智能体是怎么自己创建的

一句话：**大模型负责"想"，我们后端的工具负责"做"**。没有使用任何外部 Agent 框架，
全部在现有 Flask 系统上实现。按"请了一个项目秘书"的思路分四层搭建：

### 第 1 层：大脑（大模型接入）

- 封装统一的 AI 服务模块（`ai_service`），对接任意 OpenAI 兼容的大模型
  （当前接入 DeepSeek），支持普通对话、流式输出、工具调用三种模式；
- 模型/密钥通过环境变量配置，换厂商不改代码。

### 第 2 层：手脚（工具层）

- 把系统现有的 **26 个业务接口包装成"工具"**，每个工具定义：名称、功能描述、
  参数格式（JSON Schema），例如 `create_task`（创建任务）、
  `analyze_my_weekly_report`（周报 AI 分析）；
- **关键设计：大模型只负责决定"调用哪个工具、填什么参数"，真正的执行和
  权限校验都在我们后端完成**——学生调不动教师的操作，改不了别人的任务；
- 新增工具只需写一个处理函数并注册，不用动大模型。

### 第 3 层：工作流（编排层）

- **对话循环**：用户提问 → 大模型决定是否调工具 → 后端执行并把结果返回给模型 →
  模型组织回答 → 最多循环 5 轮；
- **需求拆解流程**：模糊需求 → 大模型输出结构化方案（项目 + 里程碑 + 任务）→
  页面展示给用户确认 → 确认后才真正创建，防止 AI 乱建数据；
- **周报分析流程**：提交周报 → 大模型比对任务要求 → 生成完成度评分、风险与审核报告；
- **定时提醒**：后台线程周期扫描任务到期、周报未交，自动生成站内通知（带去重）。

### 第 4 层：记忆与界面

- 对话记录持久化到数据库，按成员隔离，可新建/切换/重命名/删除对话；
- 前端 AI 助手页面（智能对话 / 需求拆解 / 我的周报），SSE 流式输出打字机效果。

### 一次真实调用长什么样

用户问："列出我的任务"

1. 大模型收到问题，判断需要数据，返回"调用 `list_my_tasks` 工具，参数 {}"；
2. 我们后端执行该工具，查询数据库，把任务列表返回给大模型；
3. 大模型把结果整理成中文回答："你当前有 2 个任务：……"；
4. 前端逐字显示回答，同时显示 ✓ list_my_tasks 工具执行标签。
